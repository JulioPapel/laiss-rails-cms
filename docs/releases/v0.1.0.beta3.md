# laiss-rails-cms 0.1.0.beta3

Corrective release. Two problems with `0.1.0.beta2`, both found by installing that
release into a fresh app rather than by reading it.

## If you installed beta2

Install `0.1.0.beta3` instead, and add an asset pipeline if you do not already
have one:

```ruby
# Gemfile
gem "laiss_cms", git: "https://github.com/JulioPapel/laiss-rails-cms.git", tag: "v0.1.0.beta3"
gem "devise", "~> 4.9"   # optional, only for the bundled sign-in
gem "propshaft"          # only if your app has no asset pipeline
```

Nothing else changes. No migrations, no config renames, no data changes — replace
the tag and run `bundle install`.

`v0.1.0.beta2` stays published and is not retracted. It is a real tag with real
code; it is simply superseded.

## An app without an asset pipeline had a broken admin

Every admin page returned 500:

```
NoMethodError: undefined method 'assets' for an instance of
Rails::Application::Configuration
```

The admin layout renders its stylesheets and JavaScript through the pipeline, and
`importmap-rails` reads `config.assets`. Rails' `--minimal` template ships neither
propshaft nor sprockets, so `config.assets` did not exist and the failure surfaced
inside a template — an error naming neither this engine nor the fix.

The engine now checks for a pipeline at boot and stops with a message that says
what is missing and what to add:

```
LaissCms needs an asset pipeline and this app has neither propshaft nor sprockets.
...
Add one line to your Gemfile:

    gem "propshaft"
```

A pipeline remains a requirement rather than something to tolerate: the admin is
the whole surface of this engine, and the admin routes are always drawn with no way
to switch them off. An admin that renders without styles or JavaScript is not a
degraded experience worth supporting — it is a broken one. Failing at boot with the
fix is strictly better than a 500 on the first request.

It is still not a gem dependency, because either propshaft or sprockets satisfies
it and forcing one on apps that already have the other would be rude.

This is now a gate. `script/gates` builds a throwaway app with no pipeline and
asserts the boot fails with that message. The check was verified to fail when the
guard is removed, so it is not a test that passes vacuously.

## `script/gates` did not prepare the test database

In a fresh clone, both Ruby gates failed with `no such table:
laiss_cms_attachments`. The specs need the dummy app's test database created and
migrated, and `script/gates` had never done it — it passed only on a working copy
whose database already existed from earlier runs.

CI was always correct: `ci.yml` runs `rake laiss_cms:test:prepare` as its own step.
The gap was in the one command the release notes tell you to trust. The gate now
prepares the database when the tables are missing, and skips the work when they
already exist.

## Verifying this release

```bash
git clone git@github.com:JulioPapel/laiss-rails-cms.git
cd laiss-rails-cms
git checkout v0.1.0.beta3
bundle install && pnpm install
script/gates
```

`script/gates` runs fourteen checks and prints a pass/fail table with counts. It
fails if a spec count drops, not only if a command exits non-zero, so a suite that
silently stopped loading is caught. One of the fourteen builds a scratch Rails app
and checks the asset-pipeline behaviour above.

**GitHub Actions still cannot run on this repository** — every job fails before
reaching a runner because the account is locked for billing. CI status is not
evidence for this release. The evidence is the local run above, which was performed
from a cold clone at this tag, from scratch.

## Unchanged from beta2

The one-gem packaging, the optional Devise integration, the isolation fixes for the
spec suite, and the redirect and mailer bug fixes. See
[`v0.1.0.beta2.md`](v0.1.0.beta2.md) for those.
